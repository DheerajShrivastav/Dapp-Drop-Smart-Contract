Stateful-fuzz invariant suites (`test/invariant/`) — each pairs a `*Handler.sol` (fuzzed actions + ghost accounting) with a `*.invariant.t.sol` (assertions):
- **`EscrowSolvency.invariant.t.sol`** (3 invariants) — drives create/fund/settle → claim → sweep across many ERC20 campaigns sharing one reward token. **Found and pinned a real bug** (see `docs/SECURITY_FINDINGS.md` #3): `claimERC20` didn't check `_erc20Swept`, allowing a cross-campaign drain. Now fixed and asserted: `invariant_globalTokenAccounting`, `invariant_perCampaignBacked`, `invariant_distributedLeqEscrowed`.
- **`FeeOnTransferEscrowSolvency.invariant.t.sol`** (3 invariants) — the same three properties as `EscrowSolvency.invariant.t.sol`, fuzzed against a fee-on-transfer ERC20 (`FeeOnTransferMock`, 5% skimmed in transit) instead of a standard token, to confirm `fundCampaignERC20`'s balance-diff fix (see `docs/SECURITY_FINDINGS.md`) holds solvent across long random sequences, not just the fixed points the unit suite (`test/FeeOnTransferERC20.t.sol`) checks. `ghost_totalFunded` tracks the amount *actually received* per funding call (measured the same way the contract itself measures it), not the nominal amount requested, and the per-campaign allocation cap is sized off that received amount so claims stay non-vacuous. **Validated non-vacuous with a negative control before merge**: temporarily reverting `fundCampaignERC20` itself (in `src/CampaignManagement.sol`) to trust the nominal `_amount` instead of the measured `received` amount — i.e., reintroducing the exact bug PR #12 fixed, with the handler's own tracking left correct — made `invariant_perCampaignBacked` fail immediately on the very first funding call, confirming the suite actually catches a regression in the production fix rather than passing vacuously. (A related but different experiment — breaking the *handler's* own ghost-tracking instead of the contract — fails a different invariant, `invariant_globalTokenAccounting`, since that invariant is the one wired to `ghost_totalFunded`; `invariant_perCampaignBacked` reads escrowed/distributed straight from the contract and never references that ghost variable, so it's specifically the contract-fix negative control that exercises it.)
- **`NFTInventory.invariant.t.sol`** (4 invariants) — same lifecycle for ERC721 (unique tokenIds) and ERC1155 (single shared asset id across all campaigns, deliberately fuzzing the commingled-pool case). Confirmed the NFT design does **not** have the ERC20 bug — `claimNFT` and `withdrawUnclaimed*` share the same per-campaign map. Handler deploys an `NFTSettlementModule` and drives all settlement calls (`setNFTMerkleRoot`/`claimNFT`/`withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155`) through it, mirroring the unit-test wiring.
- **`AttestationVersion.invariant.t.sol`** (3 invariants) — adversarially fuzzes stale-version replay, skip-ahead, non-signer, and expired-deadline attempts against the signed-attestation replay guard via `try/catch`; confirms the on-chain version only ever advances by exactly 1 via a genuinely valid signature. `invariant_noUnexpectedAcceptances` explicitly asserts a `ghost_unexpectedAcceptances` counter stays 0, on top of the two pre-existing live-state cross-checks (`invariant_versionMatchesGhostModel`/`invariant_completionMatchesLastAcceptedAttestation`). The four attacker functions record outcomes via ghost counters and return normally rather than reverting on unexpected success — see Known Issues below for why (a prior revert-based version of this handler silently passed a negative control even though the two cross-check invariants are independent of its own bookkeeping, because the loud revert erased the bypassed call's own state mutation, not just a ghost write). (An earlier `afterInvariant()` coverage-sanity hook was removed — it was a per-run check that could legitimately fail on a short run that happened to miss one path, and Foundry replays such failures as cached deterministic counterexamples; the call-summary table already shows both paths are exercised copiously.)
- **`OnChainReward.invariant.t.sol`** (4 invariants) — RANK_TIERED settlement + per-campaign module pinning, including a `rotateGlobalModule` handler action that swaps the admin-rotatable default mid-run: `invariant_globalTokenAccounting` (`sum(on-chain claims) <= escrowed`, exactly), `invariant_claimAtMostOncePerParticipant` (`claim()` deliberately retries a participant who already succeeded, so this exercises the module's own double-claim guard rather than trusting the handler), `invariant_rankAssignmentsAreDistinct` (no duplicate ranks within a campaign), `invariant_pinnedModuleNeverChanges` (a campaign's pin never moves, across any number of rotations). Validated non-vacuous with a negative control before merge (temporarily broke `getCampaignRewardModule`, confirmed the pin invariant failed, reverted).
- **`RootDisputeWindow.invariant.t.sol`** (3 invariants) — covers both the ERC20 and NFT Merkle root dispute window (`ROOT_DISPUTE_WINDOW`), including a `warpForward` handler action (mirrors `sweep`'s big grace-period warp in the other suites) so both the "claim succeeds" and "claim correctly rejected" branches get meaningfully exercised. A ghost mirror (`erc20ExpectedClaimableAt`/`nftExpectedClaimableAt`) independently reconstructs the rearm rule (rearm only on a genuine root-value change) and is cross-checked every run against `getERC20ClaimableAt`/`getNFTClaimableAt`: `invariant_ERC20ClaimableAtMatchesGhostRearmRule`, `invariant_NFTClaimableAtMatchesGhostRearmRule` — note these two check *timing*, not that a claim actually respected it. `attemptERC20Claim`/`attemptNFTClaim` predict, per attempt, whether a claim MUST succeed or MUST revert `RootDisputeWindowActive`, and record the outcome (success/revert/wrong-revert-reason) into six ghost counters rather than reverting on the unexpected branch — asserted by `invariant_NoDisputeWindowViolations`, the invariant that actually checks the property this suite exists for. See Known Issues below: an earlier revert-based version of the handler passed a negative control with **zero failures across all invariants** (disabling either contract's dispute-window check), since this suite had no independent cross-check at all for "a claim never succeeds before claimableAt" — the loud revert was the *only* thing watching, and it didn't work. Caught a real bug in the handler itself during development (a missing `vm.prank(participant)` meant every claim executed as the handler contract, so proof verification never matched) — surfaced via trace inspection during that development pass, predating the fail_on_revert blind spot found later while re-verifying this suite. A deliberate "did both outcomes get exercised" liveness invariant was **not** added: Foundry evaluates every `invariant_*` once immediately after `setUp()` too (runs=0, calls=0), so an `assertGt(ghost, 0)` check fails unconditionally regardless of what happens afterward — this project already hit and removed the equivalent `afterInvariant()` coverage hook on `AttestationVersion.invariant.t.sol` for the same reason (see Known Issues). Non-vacuousness was instead confirmed manually: a forced single continuous run (`FOUNDRY_INVARIANT_RUNS=1 FOUNDRY_INVARIANT_DEPTH=3000`) showed all four ghost counters nonzero (`erc20Success=104, erc20Revert=1, nftSuccess=80, nftRevert=3`) with zero unexpected outer reverts.
- **`RewardConfigAccessControl.invariant.t.sol`** (2 invariants) — closes the last open item on the hardening backlog: access-control fuzzing on `configureERC20Reward`/`depositERC721Rewards`/`depositERC1155Rewards`. Unlike every prior suite (which fuzzes a single host — the handler itself), this one runs 3 distinct hosts, each with its own campaigns, and repeatedly has each attempt those three functions on the OTHER hosts' campaigns — exercising per-campaign host-*binding* (`campaign.host == msg.sender`), not just `HOST_ROLE` possession. `invariant_UnauthorizedAttemptsNeverSucceed` and `invariant_ConfiguredTokenMatchesLegitimateHostOnly` (an independent live-state cross-check). **Notably does NOT use the loud-revert pattern** — see Known Issues below for why, discovered while building this suite. Negative-control validated (hand-disabled `onlyHost`'s ownership check, confirmed both invariants fail, reverted).

Claim tests build real Merkle proofs via Solidity helpers matching the OZ StandardMerkleTree + sorted-pair convention. Signature tests/handlers build real EIP-712 digests/signatures via `vm.sign` against a locally-computed domain separator mirroring `CampaignStorage`'s `TASK_ATTESTATION_TYPEHASH`.

## Known issues
- CI (`.github/workflows/test.yml`) runs `forge fmt --check`, `forge build --sizes`, `forge test -vvv` under `FOUNDRY_PROFILE=ci`, but `foundry.toml` defines no `[profile.ci]` (falls back to default). Cosmetic.
- `actions/checkout@v4` in CI triggers a Node 20 deprecation warning — non-blocking, worth bumping to v5.
- `block.timestamp` comparison lints (rate-limit/anti-spam) — informational.
- **Contract size**: `Web3Campaigns` runtime is 23,988B against the 24,576B EIP-170 limit — **~588B headroom.** The permissionless-`endCampaign` change *recovered* ~57B (dropping the `onlyHost` modifier + its host-address SLOAD/compare outweighed the added `CampaignNotFound` check), partly offsetting the participant-limit pass's ~367B before it. Removing an access-control modifier is one of the few edits that frees space rather than consuming it. The satellite-contract pattern (`OnChainRewardModule`/`FeeModule`/`NFTSettlementModule`) remains the strategy for anything with meaningful *logic*. **Check `forge build --sizes` before writing any code that touches `Web3Campaigns`/`CampaignManagement`/`ParticipantManagement`/`CampaignViewFunctions`/`CampaignStorage`, not just before committing** — headroom is still under 600B. (Invariant/handler and unit test files do not affect this — they're not part of the deployed contract.)
- A handler bug encountered during development, worth remembering for future ERC1155 test/handler contracts: OZ's `_mint` invokes the ERC1155 receiver hook, so any contract that receives freshly-minted ERC1155 tokens (e.g. a fuzz handler) must inherit `ERC1155Holder` or implement `onERC1155Received` — otherwise the mint reverts silently under `fail_on_revert=false`, which can make an invariant vacuously true. Always sanity-check a new handler's call-summary table for suspicious 100%-revert rows.
- Using `vm.expectRevert` **inside** a stateful-fuzz handler under `fail_on_revert=false` is fragile: if the wrapped call unexpectedly succeeds (a real bug), `vm.expectRevert`'s own mismatch failure reverts the whole handler call — undoing the buggy state change too — and the fuzzer silently discards it as "just another revert," masking the bug.
- **Correction, found via `RewardConfigAccessControl.invariant.t.sol`'s negative control: the previous line's own recommended fix — `try/catch` with a loud `revert("...")` on the unexpected-success branch (`AttestationVersionHandler.sol`, `RootDisputeWindowHandler.sol`) — has the SAME flaw it was meant to solve.** Any revert from a handler call, deliberate or not, is *also* silently discarded under `fail_on_revert=false`, and any ghost-counter write made in that same call (including the one meant to signal the bug) is rolled back with it. Verified directly: hand-breaking `onlyHost`'s check and re-running `RewardConfigAccessControl.invariant.t.sol` with the loud-revert version of its handler produced **zero failures**, even though the bypass genuinely occurred. **The actual fix: don't revert on the unexpected-success branch at all** — record the outcome in a ghost counter and let the call return normally (so the write survives), then assert the ghost counter `== 0` inside a view `invariant_*` function, which fails the run via forge-std's non-reverting failure mechanism rather than through control flow the fuzzer intercepts. Confirmed this version fails correctly on the same negative control. **Update: `AttestationVersionHandler.sol` and `RootDisputeWindowHandler.sol` have since been re-verified and fixed the same way** (see [SECURITY_FINDINGS.md](SECURITY_FINDINGS.md)) — both genuinely had the bug: disabling the checks they were built to catch produced zero failures with the old pattern in both cases (`RootDisputeWindowHandler`'s exposure was total, since its two pre-existing invariants only checked claimable-*timing*, never that a claim actually respected it), and both now correctly fail the same negative controls after conversion.

## Deploy
