# Next Steps — Web3Campaigns v0.3+

> Pick-up list. v0.3 escrow + Merkle settlement, Phase 2 signature verification, the invariant-test hardening pass (incl. a real security fix), `cancelCampaign`, on-chain tiered settlement + per-campaign module pinning, its invariant suite, the Merkle root dispute window, its invariant suite, the protocol fee module, the NFT settlement module extraction, fee-on-transfer ERC20 support, its invariant coverage, the hardening sweep (withdrawETH treasury restriction + `.code.length` token checks + multi-leaf NFT proof test), sponsored (gasless) claims + the Humanity gating spec, deployment readiness (full-system deploy script + smoke test + runbook), reward-configuration access-control invariant coverage, the loud-revert re-verification, and per-campaign `MAX_PARTICIPANTS_LIMIT` enforcement are all merged to `dev` (PR #1–#19; VERSION 0.5.0). Permissionless `endCampaign` (the abandoned-host lockup fix + platform-keeper automation), plus two review-caught follow-ups extending `cancelCampaign` to accept `Ended` for zero-participant campaigns and then closing a settlement-commitment rug-pull the first follow-up alone had reopened, are in progress on `feature/permissionless-lifecycle`. Ordered roughly by priority.

## Hardening / open items (on the current model)

- [x] **Fuzz / invariant tests.** Merged to `dev` via PR #3: escrow-solvency (`sum(ERC20 claims) <= escrowed`), NFT inventory (claimed <= deposited, ERC721 + ERC1155), and attestation-version replay-guard invariants. **Found and fixed a real HIGH-severity bug that had been live on `dev`**: `claimERC20` didn't check `_erc20Swept`, letting a late claim on a swept campaign drain a *different* campaign's escrow (ERC20 escrow is a commingled pool). See `docs/SECURITY_FINDINGS.md` #3 and `test/invariant/EscrowSolvency.invariant.t.sol`. The `no-mistakes` pipeline review pass also caught a methodological flaw in the test design itself (`vm.expectRevert` inside a `fail_on_revert=false` handler could mask a real bypass) and a flaky per-run coverage guard — both fixed.
- [x] **Per-campaign reward-module pinning (on-chain tiered settlement).** Replaced sole reliance on the global `_onChainRewardModule` pointer: each campaign pins its module at adoption (`_campaignRewardModule[id]`), `payOnChainReward` authorizes against that pin (not the rotatable global default), and `claimReward` self-checks authority before computing a payout. Closes a mid-campaign rotation hazard (rank/score desync / payout lockout) — see `docs/SECURITY_FINDINGS.md`. Done on `fix/per-campaign-module-pinning`.
- [x] **RANK_TIERED rank permanence vs. revocation — resolved (by design).** A completion rank, once assigned, is monotonic and never un-assigned. A signer revoking a required task afterward does **not** erase the historical rank, but sets `_currentlyQualified = false`, which takes precedence and blocks payout **until the participant is re-verified in full**. Documented in `OnChainRewardModule.sol` (`notifyTaskCompletion` / `claimReward`).
- [x] **Allocation-fairness dispute window.** `ROOT_DISPUTE_WINDOW` (24h): publishing a genuinely new ERC20 or NFT Merkle root starts a window during which `claimERC20`/`claimNFT` reject claims against it (`RootDisputeWindowActive`), giving the community time to catch an unfair root and escalate (e.g. `emergencyPause`) before funds move. Rearmed only when the root's value actually changes — a republish of the byte-identical root is a no-op (closes a self-griefing gap a reviewer caught pre-merge). A delay-based mitigation, not full on-chain dispute resolution — see `docs/SECURITY_FINDINGS.md`. Sweeps need no separate gating: `CLAIM_GRACE_PERIOD` (30 days) already dominates the window. Done on `feature/merkle-root-dispute-window` (PR #8).
- [x] **Root dispute window invariant coverage.** `RootDisputeWindow.invariant.t.sol` fuzzes both the ERC20 and NFT paths with a ghost mirror of the rearm rule, cross-checked against `getERC20ClaimableAt`/`getNFTClaimableAt` every run, plus per-attempt success/revert prediction via try/catch (this project's established loud-revert-on-wrong-outcome pattern). Caught a real bug in the handler itself (a missing `vm.prank`) during development. Done on `feature/root-dispute-window-invariant`.
- [x] **Fee-on-transfer ERC20 handling.** `fundCampaignERC20` now measures the amount actually received via `balanceOf(this)` before/after the pull, instead of trusting the caller-supplied `amount` — a fee-on-transfer token can no longer over-credit escrow beyond what the contract actually custodies. Protocol fee (if registered) is computed on the received amount too. New error `Web3Campaigns__NoFundsReceived` for the 100%-skim degenerate case. Standard tokens: byte-for-byte unchanged behavior. See `docs/SECURITY_FINDINGS.md`. Done on `feature/fee-on-transfer-erc20` (PR #12).
- [x] **Fee-on-transfer invariant coverage.** Follow-up flagged during PR #12's review: `EscrowSolvencyHandler` (the stateful-fuzz suite designed to catch escrow drift across long random sequences) only ever wired up a standard `ERC20Mock`, so it couldn't exercise the fee-on-transfer fix above. New dedicated suite `FeeOnTransferEscrowSolvency.invariant.t.sol` fuzzes the same three properties against a `FeeOnTransferMock` token. Validated non-vacuous with a negative control (temporarily reverted the received-amount tracking, confirmed the suite fails immediately). See `docs/SECURITY_FINDINGS.md`. Done on `feature/fee-on-transfer-invariant`.
- [x] **Multi-leaf NFT proof test** in the unit suite. `test_ClaimERC721_MultiLeafTree_BothParticipantsClaim` (real 2-leaf tree, two participants, genuine single-sibling proofs) + `_RevertsOnWrongProof`. Done in the hardening sweep (`feature/hardening-sweep`).
- [x] **Reward-configuration invariant coverage.** New `RewardConfigAccessControl.invariant.t.sol` fuzzes 3 distinct hosts each attempting `configureERC20Reward`/`depositERC721Rewards`/`depositERC1155Rewards` on the OTHER hosts' campaigns — must always revert `CallerIsNotHost`. Negative-control validated (hand-disabled `onlyHost`'s check, confirmed the suite fails). **Also surfaced a methodological finding**: this project's established "loud revert on unexpected success" handler pattern (`AttestationVersionHandler`/`RootDisputeWindowHandler`) doesn't actually fail an invariant run under `fail_on_revert=false` — any revert, including a deliberate one, is silently discarded along with the ghost-counter write meant to signal the bug. Fixed in the new suite (ghost-counter-only, no revert); the two pre-existing suites were **not** retroactively changed (flagged as a follow-up) — see `docs/SECURITY_FINDINGS.md` and `docs/TEST_AND_BUILD.md` Known Issues. Done on `feature/reward-config-invariant`.
- [x] **`withdrawETH` treasury restriction (low).** Replaced the arbitrary `_to` with a stored, admin-settable `_treasury` (`setTreasury`); `withdrawETH()` now takes no destination. Clears Slither's `arbitrary-send-eth` flag (269 → 268). API-breaking but admin-only/pre-launch. Done in the hardening sweep (`feature/hardening-sweep`).
- [x] **Deployment readiness — the deploy script was dangerously stale.** It deployed `Web3Campaigns` alone, predating the entire satellite architecture: a deployment from it would have had **dead NFT rewards** (deposits revert, no `NFTSettlementModule` registered), **no tiered rewards** (`NotOnChainRewardModule`), and a **permanently-reverting `withdrawETH`** (no treasury) — plus a stale `^0.8.20` pragma. Now deploys + wires the full system with env-var config (all defaulting safely; `FEE_BPS=0` = no fees, the beta default), guarded by `test/DeploymentSmoke.t.sol` which calls the script's real `deploy()` and drives all three reward paths end-to-end (negative-control validated: reverting the script to its old shape fails 4 of 9). Runbook: `docs/DEPLOYMENT.md`. Done on `feature/deployment-readiness`.
- [x] **Repo-wide `forge fmt`.** Stale item — `forge fmt --check` now passes cleanly (verified 2026-07-13); resolved incidentally across the recent PR series, each of which runs `forge fmt` before committing.
- [x] **Re-verify the pre-existing loud-revert invariant handlers — DONE, both genuinely had the bug.** `AttestationVersionHandler.sol` and `RootDisputeWindowHandler.sol` both used "try/catch + loud revert on unexpected success", which `RewardConfigAccessControl.invariant.t.sol`'s negative control showed does NOT actually fail an invariant run under `fail_on_revert=false`. Re-verified each by temporarily reintroducing the exact bug the affected branch was built to catch (disabling `hasRole(SIGNER_ROLE,...)`, the deadline check, and both contracts' dispute-window checks in turn) and confirming the *suite* reported zero failures with the old pattern in every case. `RootDisputeWindowHandler`'s exposure was total — its two pre-existing invariants only ever checked claimable-*timing*, never that a claim actually respected it, so the broken loud-revert was the *only* thing standing between a real bypass and a silent green suite. Both converted to the ghost-counter-only pattern (record outcome, return normally, assert via `invariant_*`); both negative controls now correctly fail. See `docs/SECURITY_FINDINGS.md`. Done on `feature/loud-revert-reverify` (196 tests passing, test-only — no `src/` diff).

- [ ] **`grantHostRole` is intentionally open.** Founder decision (reconfirmed 2026-07-13): stays open through the testing/beta phase; will become chargeable (the staked hosting tier below) after beta ends.
- [x] **`.code.length` check** on `configureERC20Reward` / NFT deposits to reject EOA/empty token addresses early. New `_requireContract` helper + `Web3Campaigns__NotAContract` error, applied at all three token-address boundaries. Done in the hardening sweep (`feature/hardening-sweep`).
- [x] **NFT settlement module extraction.** All NFT Merkle-settlement logic + escrow bookkeeping moved out of `Web3Campaigns` into a new satellite `NFTSettlementModule` (mirroring `OnChainRewardModule`/`FeeModule`), reclaiming ~793B of entrypoint headroom (23,829B → 23,036B runtime). `Web3Campaigns` keeps all NFT custody; users call the module directly for `setNFTMerkleRoot`/`claimNFT`/`withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155`. New per-campaign pin (`_campaignNFTModule`) set at **first deposit** (earlier than the reward module's pin-at-mode-adoption), since escrow bookkeeping can precede any root ever being published — see `docs/SECURITY_FINDINGS.md`. Done on `feature/nft-settlement-module`.
- [ ] **Contract size headroom — critical, now within single-digit bytes of the EIP-170 limit.** `Web3Campaigns` runtime is 24,569B / 24,576B limit (**~7B left**). Path here: permissionless-`endCampaign` *recovered* ~57B by dropping a modifier (588B headroom), the first `cancelCampaign` follow-up (accepting `Ended`) cost ~49B back (539B), the second follow-up (settlement-commitment guard) cost ~171B more (368B), and the `SETTLER_ROLE` fallback pass cost ~361B more on top of that even AFTER a deliberate redesign to minimize it (the naive implementation would have blown the budget by 180B+ — see `docs/SECURITY_FINDINGS.md` for the three specific changes that clawed it back: an internal, not public, delay constant; caching `endTime` on the NFT module instead of a new getter; reusing the already-public `hasRole`). **There is essentially no headroom left** — any future inline addition to `Web3Campaigns`/`CampaignManagement`/`ParticipantManagement`/`CampaignViewFunctions`/`CampaignStorage`, however small, needs a `forge build --sizes` check *before* writing a single line, and should default to assuming it needs to move to a new satellite contract rather than fit inline. The satellite-contract pattern is no longer "close to mandatory" — it is now the only realistic option for new inline-entrypoint logic.

## Phase 2 (merged to `dev` via PR #2)

- [x] **Signature-based off-chain task verification.** `SIGNER_ROLE` + EIP-712 `TaskAttestation` (`{campaignId, participant, taskIndex, completed, version, deadline}`) — `verifyTaskCompletionWithSignature`/`batchVerifyTaskCompletionWithSignatures` **replace** (not run alongside) the old host-tx `verifyTaskCompletion`/`batchVerifyTaskCompletion`. Signer rotation/revocation via plain `AccessControl` `grantRole`/`revokeRole(SIGNER_ROLE, ...)`. Replay guard = per-`(participant,campaign,task)` version counter, which doubles as an update/reverification mechanism (signer can flip `completed` back to false or re-affirm it by signing the next version). Single-signer for now (no N-of-M threshold). Trust-minimized, not trustless — documented in `docs/TASK_VERIFICATION.md`. Merged to `dev` via the `no-mistakes` pipeline (PR #2), which itself caught and fixed a real bug during review (signer revocation bypassable via self-assertion — see `TaskManagedBySignature`).
- [x] **Protocol fee.** `FeeModule` (a satellite contract, mirroring `OnChainRewardModule` — no per-campaign pinning needed, since fee computation has no persistent per-campaign state to desync across a rotation) skims a flat `feeBps` at `fundCampaignERC20`, routed to a treasury. NFT deposits are out of scope for v1. Done on `feature/protocol-fee-module`.
- [x] **`cancelCampaign` + refund.** Merged to `dev` via PR #4. Allowed only in Draft/Open **and** while `campaign.totalParticipants == 0` (founder-flagged abuse concern: without the zero-participants gate, a host could let people do free work then cancel right before `Ended` to dodge paying out — closed by locking in the moment anyone genuinely engages). ERC20 refunded immediately, no grace period (safe since no root/claim was ever possible pre-Ended). NFTs reclaimed via `NFTSettlementModule.withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155`, now immediately callable (no grace wait) once `Cancelled`. New terminal `CampaignStatus.Cancelled`.

## Phase 3 (post-PMF)

- [x] **Sybil gating via Humanity Protocol — designed; zero contract changes needed today.** Founder decisions (2026-07-13): Humanity Protocol via their off-chain OAuth SDK, fully automated (no manual signing — the `SIGNER_ROLE` key signs programmatically in the backend's OAuth callback, no human/host involvement). Since Humanity Protocol has **no on-chain interface yet**, enforcement is off-chain at the three points the backend already controls: Merkle tree-build filtering (primary — unverified wallets get no leaf, so cannot claim), sponsored-claim submission checks (courtesy, not enforcement), and a required `HUMANITY_VERIFICATION` task on tiered campaigns (settled by the existing attestation path). Full spec for the backend repo: `docs/HUMANITY_GATING.md`. **Deferred until Humanity Protocol ships an on-chain registry**: a rotatable `IHumanityModule` satellite (`isVerified(address) → bool`) consulted at claim time — building it earlier would just wrap a backend-synced allowlist (same trust, extra gas). Contract work resumes when their registry launches.
- [x] **Gasless claims** — done via sponsored-claim entrypoints (`claimERC20For`/`claimNFTFor`/`claimRewardFor`): anyone (in practice the project backend, paying gas) submits a claim on behalf of an allocated account; the reward always goes to the account, never the caller. Deliberately NO meta-transaction framework (ERC-2771 would change `_msgSender()` semantics contract-wide; ERC-4337 needs no contract support and stays available independently). See `docs/SECURITY_FINDINGS.md`. Done on `feature/sponsored-claims`.
- [x] **`MAX_PARTICIPANTS_LIMIT` enforcement — done, per-campaign not global.** Founder decision: a single global cap didn't fit how differently-sized campaigns actually work, so hosts set their own cap via a new `setMaxParticipants(id, cap)` (Draft-only, `cap` 0 = unlimited, hard-capped at `MAX_PARTICIPANTS_LIMIT` (100,000) as a sanity ceiling, not a policy default). Enforced in `completeTask`/`verifyTaskCompletionWithSignature` at the same point `totalParticipants` would be incremented for a genuinely new participant — reverts `ParticipantLimitReached` once the cap is hit; never blocks a wallet already counted from completing further tasks. `JOIN_COOLDOWN` was removed rather than wired up — 1 minute wasn't meaningful sybil resistance, and real sybil resistance is the already-designed Humanity Protocol gating (`docs/HUMANITY_GATING.md`), not a timer. See `docs/SECURITY_FINDINGS.md`. Done on `feature/participant-limit`.
- [x] **Permissionless `endCampaign` — done (abandoned-host lockup fix + platform-keeper automation).** `endCampaign` was host-only, which meant a host who opened a campaign then vanished left it stuck in `Open` forever — participants could never reach `Ended`, never claim, and escrow never moved. Now anyone (in practice the platform keeper, but any participant works) can end a campaign once `block.timestamp >= endTime`; the time gate binds every caller so no one can end early. `openCampaign`/`closeCampaign` deliberately stay host-only (opening is a "config is done" judgment call; closing freezes the Merkle root and only benefits the host). Net size DECREASE (removing `onlyHost` from `endCampaign` outweighed the added existence check). See `docs/SECURITY_FINDINGS.md`. Done on `feature/permissionless-lifecycle`.
- [x] **`cancelCampaign` extended to accept `Ended`, then hardened with a settlement-commitment guard — done (two review-caught follow-ups to the `endCampaign` change above).** Making `endCampaign` permissionless meant a keeper could end a zero-participant expired campaign, which used to permanently strip that host of `cancelCampaign`'s immediate refund (they'd have been forced into the 30-day `closeCampaign` grace path for the same money). Fixed by accepting `Ended` in `cancelCampaign`'s status guard alongside Draft/Open. A second review round caught that this alone was unsafe: `totalParticipants` never tracked Merkle settlement, so a host could publish a root, let some accounts claim, then cancel to rug-pull the rest. Fixed by additionally requiring `_erc20SettlementMode == UNSET` and no NFT root ever published on the pinned `NFTSettlementModule`. `Closed` deliberately still excluded. See `docs/SECURITY_FINDINGS.md` for the full two-round writeup. Done on `feature/permissionless-lifecycle`.
- [x] **`SETTLER_ROLE` settlement-liveness fallback for abandoned Merkle campaigns — done.** Permissionless `endCampaign` (above) guaranteed a campaign reaches `Ended`, but Merkle settlement itself was still host-only — an abandoned campaign with real participants could get to `Ended` and then sit there forever with no root, nobody able to claim, `cancelCampaign` blocked, escrow stranded. A new admin-granted `SETTLER_ROLE` may now publish a fallback root (`setERC20MerkleRoot`/`NFTSettlementModule.setNFTMerkleRoot`) or close a campaign (`closeCampaign`), strictly as a last resort: only once `Ended` for `SETTLEMENT_FALLBACK_DELAY` (14 days) with no root ever published (publish) or a root already existing (close). A settler can only ever fill a vacuum — never override, correct, or race a host-published root — and the host retains full authority at all times, including after a settler acts. Composes cleanly with `cancelCampaign`'s settlement-commitment guard (a settler root counts as committed settlement identically to a host one, no guard changes needed). This is distinct from — and effectively supersedes the motivation for — the deferred "permissionless `closeCampaign`" item below: rather than opening `closeCampaign` to anyone (which the deferred item never found a fully safe design for), a role-gated, delay-gated fallback achieves the same liveness goal with a much smaller trust expansion. See `docs/SECURITY_FINDINGS.md` for the full writeup, including a real EIP-170 sizing crunch this pass required a deliberate redesign to survive. Done on `feature/settler-fallback-settlement`.
- [ ] **Staked/open hosting tier** — `selfRegisterAsHost() payable` gated by a refundable stake / creation fee, slashable on abuse (the deliberate version of today's open `grantHostRole`). Founder decision: deferred until after the testing/beta phase; open questions before building — stake amount, who adjudicates a slash, where slashed funds go.
- [ ] **Optional: a fully permissionless (not just SETTLER_ROLE-gated) `closeCampaign` (deferred from the permissionless-lifecycle pass; largely superseded by the `SETTLER_ROLE` fallback above).** `endCampaign` is permissionless, and `closeCampaign` now has a role-gated, delay-gated settler fallback, but the ORIGINAL idea here — anyone (not just a designated settler) closing once safe — remains unbuilt: it would need a time gate that respects **each root's own dispute window** (roots can be published late, and the NFT root lives on `NFTSettlementModule` — so the gate has to reason across both the ERC20 and NFT root timestamps), not just `endTime + fixed`. Given the settler fallback now covers the actual liveness need (an abandoned campaign can eventually reach `Closed`), this remaining gap is purely "should literally anyone be able to trigger it, not just a designated settler" — low value, deferred indefinitely absent a concrete need. See the permissionless-lifecycle and settler-fallback passes in `docs/SECURITY_FINDINGS.md`.
- [x] **Gas: hoist the participant-cap check earlier in `completeTask`/`_verifySingleTaskCompletion` — ATTEMPTED 2026-07-19, DROPPED for headroom reasons.** The `ParticipantLimitReached` check added in PR #19 sits after `_participantTaskCompletion[...] = true` and the call to `_notifyModuleOfCompletion`; not a security bug (atomic revert unwinds everything regardless), purely wasted gas on a doomed-to-revert at-capacity attempt. Implemented the hoist exactly as described (moved the cap check to before the on-chain verification/state writes/notify call in both functions, reusing a single early-computed `isNewParticipant`/`wasCompleted` read rather than re-deriving it later) and it worked correctly — `forge test` passed 244/244 unchanged. **But it cost 40B of `Web3Campaigns` runtime size** (24,569B → 24,609B), which — against the ~7B headroom this project is now down to (see the critical-headroom note below) — would have pushed the contract **33B over the EIP-170 limit**, an unbuildable/undeployable state. Per the hard size gate for this pass, the change was reverted rather than pursued via a satellite extraction or other creative restructuring (that trade was already decided against). `ParticipantManagement.sol` therefore has NO diff from this pass — the cap check remains exactly where PR #19 left it. Revisit only if/when `Web3Campaigns` gains meaningful headroom back (e.g., a future extraction moves more logic into a satellite), or if gas cost on the rejection path becomes an active pain point worth spending scarce headroom on deliberately.
