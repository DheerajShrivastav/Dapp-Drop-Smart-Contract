# Next Steps — Web3Campaigns v0.3+

> Pick-up list. v0.3 escrow + Merkle settlement, Phase 2 signature verification, the invariant-test hardening pass (incl. a real security fix), `cancelCampaign`, on-chain tiered settlement + per-campaign module pinning, its invariant suite, the Merkle root dispute window, its invariant suite, the protocol fee module, the NFT settlement module extraction, and fee-on-transfer ERC20 support are all merged to `dev` (PR #1–#12; VERSION 0.5.0). Fee-on-transfer invariant coverage is in progress on `feature/fee-on-transfer-invariant` (156 tests passing). Ordered roughly by priority.

## Hardening / open items (on the current model)

- [x] **Fuzz / invariant tests.** Merged to `dev` via PR #3: escrow-solvency (`sum(ERC20 claims) <= escrowed`), NFT inventory (claimed <= deposited, ERC721 + ERC1155), and attestation-version replay-guard invariants. **Found and fixed a real HIGH-severity bug that had been live on `dev`**: `claimERC20` didn't check `_erc20Swept`, letting a late claim on a swept campaign drain a *different* campaign's escrow (ERC20 escrow is a commingled pool). See `docs/SECURITY_FINDINGS.md` #3 and `test/invariant/EscrowSolvency.invariant.t.sol`. The `no-mistakes` pipeline review pass also caught a methodological flaw in the test design itself (`vm.expectRevert` inside a `fail_on_revert=false` handler could mask a real bypass) and a flaky per-run coverage guard — both fixed.
- [x] **Per-campaign reward-module pinning (on-chain tiered settlement).** Replaced sole reliance on the global `_onChainRewardModule` pointer: each campaign pins its module at adoption (`_campaignRewardModule[id]`), `payOnChainReward` authorizes against that pin (not the rotatable global default), and `claimReward` self-checks authority before computing a payout. Closes a mid-campaign rotation hazard (rank/score desync / payout lockout) — see `docs/SECURITY_FINDINGS.md`. Done on `fix/per-campaign-module-pinning`.
- [x] **RANK_TIERED rank permanence vs. revocation — resolved (by design).** A completion rank, once assigned, is monotonic and never un-assigned. A signer revoking a required task afterward does **not** erase the historical rank, but sets `_currentlyQualified = false`, which takes precedence and blocks payout **until the participant is re-verified in full**. Documented in `OnChainRewardModule.sol` (`notifyTaskCompletion` / `claimReward`).
- [x] **Allocation-fairness dispute window.** `ROOT_DISPUTE_WINDOW` (24h): publishing a genuinely new ERC20 or NFT Merkle root starts a window during which `claimERC20`/`claimNFT` reject claims against it (`RootDisputeWindowActive`), giving the community time to catch an unfair root and escalate (e.g. `emergencyPause`) before funds move. Rearmed only when the root's value actually changes — a republish of the byte-identical root is a no-op (closes a self-griefing gap a reviewer caught pre-merge). A delay-based mitigation, not full on-chain dispute resolution — see `docs/SECURITY_FINDINGS.md`. Sweeps need no separate gating: `CLAIM_GRACE_PERIOD` (30 days) already dominates the window. Done on `feature/merkle-root-dispute-window` (PR #8).
- [x] **Root dispute window invariant coverage.** `RootDisputeWindow.invariant.t.sol` fuzzes both the ERC20 and NFT paths with a ghost mirror of the rearm rule, cross-checked against `getERC20ClaimableAt`/`getNFTClaimableAt` every run, plus per-attempt success/revert prediction via try/catch (this project's established loud-revert-on-wrong-outcome pattern). Caught a real bug in the handler itself (a missing `vm.prank`) during development. Done on `feature/root-dispute-window-invariant`.
- [x] **Fee-on-transfer ERC20 handling.** `fundCampaignERC20` now measures the amount actually received via `balanceOf(this)` before/after the pull, instead of trusting the caller-supplied `amount` — a fee-on-transfer token can no longer over-credit escrow beyond what the contract actually custodies. Protocol fee (if registered) is computed on the received amount too. New error `Web3Campaigns__NoFundsReceived` for the 100%-skim degenerate case. Standard tokens: byte-for-byte unchanged behavior. See `docs/SECURITY_FINDINGS.md`. Done on `feature/fee-on-transfer-erc20` (PR #12).
- [x] **Fee-on-transfer invariant coverage.** Follow-up flagged during PR #12's review: `EscrowSolvencyHandler` (the stateful-fuzz suite designed to catch escrow drift across long random sequences) only ever wired up a standard `ERC20Mock`, so it couldn't exercise the fee-on-transfer fix above. New dedicated suite `FeeOnTransferEscrowSolvency.invariant.t.sol` fuzzes the same three properties against a `FeeOnTransferMock` token. Validated non-vacuous with a negative control (temporarily reverted the received-amount tracking, confirmed the suite fails immediately). See `docs/SECURITY_FINDINGS.md`. Done on `feature/fee-on-transfer-invariant`.
- [ ] **Multi-leaf NFT proof test** in the unit suite (current NFT unit tests use single-leaf roots; the invariant suite covers many campaigns but each still with a single-leaf root).
- [ ] **Reward-configuration invariant coverage** — current invariants focus on the settlement/claim/sweep lifecycle; access-control fuzzing on `configureERC20Reward`/deposits is still open.
- [ ] **`withdrawETH` treasury restriction (low).** Replace the arbitrary `_to` with a stored, admin-settable treasury to clear the `arbitrary-send-eth` flag.
- [ ] **Repo-wide `forge fmt`.** Repo does not pass `forge fmt --check` (pre-existing). Do a single formatting pass so CI's `forge fmt --check` goes green — as its own commit to keep diffs reviewable.
- [ ] **`grantHostRole` is intentionally open.** Revisit when adding the staked/curated hosting model (founder decision to leave open for now).
- [ ] **`.code.length` check** on `configureERC20Reward` / NFT deposits to reject EOA/empty token addresses early.
- [x] **NFT settlement module extraction.** All NFT Merkle-settlement logic + escrow bookkeeping moved out of `Web3Campaigns` into a new satellite `NFTSettlementModule` (mirroring `OnChainRewardModule`/`FeeModule`), reclaiming ~793B of entrypoint headroom (23,829B → 23,036B runtime). `Web3Campaigns` keeps all NFT custody; users call the module directly for `setNFTMerkleRoot`/`claimNFT`/`withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155`. New per-campaign pin (`_campaignNFTModule`) set at **first deposit** (earlier than the reward module's pin-at-mode-adoption), since escrow bookkeeping can precede any root ever being published — see `docs/SECURITY_FINDINGS.md`. Done on `feature/nft-settlement-module`.
- [ ] **Contract size headroom.** `Web3Campaigns` runtime is 23,258B / 24,576B limit (~1,318B left after the fee-on-transfer fix's balance-diff logic + new error cost ~222B). Still comfortable, but the satellite-contract pattern (`OnChainRewardModule`/`FeeModule`/`NFTSettlementModule`) should stay the default for any future feature needing meaningful logic — inline logic changes like this one and wiring a satellite in both cost real bytes. Watch `forge build --sizes` before every change.

## Phase 2 (merged to `dev` via PR #2)

- [x] **Signature-based off-chain task verification.** `SIGNER_ROLE` + EIP-712 `TaskAttestation` (`{campaignId, participant, taskIndex, completed, version, deadline}`) — `verifyTaskCompletionWithSignature`/`batchVerifyTaskCompletionWithSignatures` **replace** (not run alongside) the old host-tx `verifyTaskCompletion`/`batchVerifyTaskCompletion`. Signer rotation/revocation via plain `AccessControl` `grantRole`/`revokeRole(SIGNER_ROLE, ...)`. Replay guard = per-`(participant,campaign,task)` version counter, which doubles as an update/reverification mechanism (signer can flip `completed` back to false or re-affirm it by signing the next version). Single-signer for now (no N-of-M threshold). Trust-minimized, not trustless — documented in `docs/TASK_VERIFICATION.md`. Merged to `dev` via the `no-mistakes` pipeline (PR #2), which itself caught and fixed a real bug during review (signer revocation bypassable via self-assertion — see `TaskManagedBySignature`).
- [x] **Protocol fee.** `FeeModule` (a satellite contract, mirroring `OnChainRewardModule` — no per-campaign pinning needed, since fee computation has no persistent per-campaign state to desync across a rotation) skims a flat `feeBps` at `fundCampaignERC20`, routed to a treasury. NFT deposits are out of scope for v1. Done on `feature/protocol-fee-module`.
- [x] **`cancelCampaign` + refund.** Merged to `dev` via PR #4. Allowed only in Draft/Open **and** while `campaign.totalParticipants == 0` (founder-flagged abuse concern: without the zero-participants gate, a host could let people do free work then cancel right before `Ended` to dodge paying out — closed by locking in the moment anyone genuinely engages). ERC20 refunded immediately, no grace period (safe since no root/claim was ever possible pre-Ended). NFTs reclaimed via `NFTSettlementModule.withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155`, now immediately callable (no grace wait) once `Cancelled`. New terminal `CampaignStatus.Cancelled`.
