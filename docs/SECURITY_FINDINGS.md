# Security & Correctness Findings — Web3Campaigns

> Original code-audit findings, annotated with current status through the `cancelCampaign` feature pass (`feature/cancel-campaign`, forked from `dev` post-invariant-hardening merge). Verify line numbers before acting.

## Status legend
✅ FIXED · 🟡 OPEN · 🔵 INTENTIONAL (founder decision) · ⏳ ADDRESSED IN PROGRESS

## HIGH

1. 🔵 **`grantHostRole` is unguarded** (CampaignManagement.sol) — anyone can self-grant `HOST_ROLE`. **Left open intentionally by founder decision (for now).** Revisit when adding the staked/curated hosting model.
2. ✅ **ERC20 rewards pulled from host's live wallet** — **FIXED in Stage B1.** Rewards are now escrowed in the contract (`fundCampaignERC20`) and paid from escrow via Merkle settlement (`claimERC20`). No host-pull, no allowance-revoke brick, no rug. See [[REWARD_SYSTEM]].
3. ✅ **Cross-campaign ERC20 escrow drain via `claimERC20` after sweep** — **FOUND AND FIXED by the escrow-solvency invariant suite** (`test/invariant/EscrowSolvency.invariant.t.sol`), not by manual review, and was **live on `dev`** (shipped in B1) before this fix. `claimERC20` never checked `_erc20Swept` despite a code comment claiming it did. Because ERC20 escrow is a single commingled token balance (unlike NFTs, which are earmarked per campaign), after a host swept campaign A's unclaimed funds back to themselves post-grace, a late claimant on A could still claim — paid out of **campaign B's** escrow, leaving B underwater. Fixed: `claimERC20` now reverts `AlreadySwept` once a campaign has been swept. Regression test: `test_ClaimERC20_BlockedAfterSweep_NoCrossCampaignDrain`.

## MEDIUM

4. ✅ **Silent zero-reward claims** (FCFS/TIERED/pool-exhaustion) — **FIXED** for ERC20 (B1) and NFT (B2): only winners with a valid proof can claim; `InsufficientEscrow`/`NFTNotEscrowed` revert rather than silently paying 0. Legacy NFT pool path removed in B2.
5. ✅ **On-chain hold verification broken** (52-byte vs 64-byte `abi.decode`) — **FIXED in Stage A.** `completeTask` now requires the correct 64-byte `abi.encode(address,uint256)` for `ONCHAIN_HOLD_ERC20/721`. (Tests in `test/StageAFixes.t.sol`.)
6. ✅ **Claim-rank front-running** (TIERED/FCFS earliest-claimer advantage) — **FIXED** for ERC20 (B1) and NFT (B2): allocations are predetermined in the Merkle tree, not by claim order.
7. ✅ **`ONCHAIN_TX` task hard-reverts / bricks campaigns** — **FIXED in Stage A.** No longer reverts in `completeTask` (now `NotSelfVerifiable`); is settled via `verifyTaskCompletionWithSignature`/`batchVerifyTaskCompletionWithSignatures` (Phase 2 — replaced the old host-tx `verifyTaskCompletion`/`batchVerifyTaskCompletion`). `ONCHAIN_HOLD_*` remain self-verified and signer-unoverridable.
14. ⏳ **Merkle root allocation fairness has no on-chain recourse** — **PARTIALLY ADDRESSED** via `ROOT_DISPUTE_WINDOW` (24h): `claimERC20`/`claimNFT` reject claims against a root until that window elapses since its (re-)publish, giving the community time to catch an unfair allocation and escalate (e.g. `emergencyPause`) before funds move. This is a **delay-based mitigation, not full on-chain dispute resolution** — there is still no on-chain flagging/veto mechanism, just time for off-chain detection. See the "New surface" note below.

## LOW / INFORMATIONAL

8. ✅ **`_suspiciousActivityScore` dead state** — **FIXED in Stage A.** Wired via `MODERATOR_ROLE` + `Web3Campaigns.flagAccount(user, score)` + `AccountFlagged` event; gate in `completeTask` now functional.
9. ✅ **`endCampaign` comment/code contradiction** — **FIXED in Stage A** (comment corrected; behavior = end only at/after `endTime`, no early end).
10. 🟡 **`withdrawETH` arbitrary `_to`** (admin-gated, low risk) — still present; deferred. Consider restricting to a stored treasury.
11. ✅ **Unguarded external-call loops** — claims are single-transfer (ERC20 `safeTransfer`; NFT one token per claim). Deposit/sweep loops are host-only, capped at 100/call, and `nonReentrant`.
12. ✅ **Pause coverage gap on `createCampaign`** — **FIXED in Stage A** (virtual + `whenNotPaused` wrapper). The other reward/host functions were already pause-gated via the virtual `onlyHost` override.
13. 🟡 `== 0` existence checks (id-sentinel `incorrect-equality`) — low risk by design; unchanged.

## New surface added in the cancelCampaign pass (review focus)
- **`cancelCampaign` — bait-and-switch griefing path closed by zero-participants gate.** The function is only callable while `totalParticipants == 0`. Once one participant has completed any task the campaign is permanently locked in (`CampaignHasParticipants`). This was an explicit founder requirement: without the gate a host could let participants do free work then cancel right before `Ended` to avoid paying out. Tested with an explicit abuse-vector test (`test_CancelCampaign_RevertsOnceAParticipantHasEngaged` in `test/CancelCampaign.t.sol`).
- **ERC20 refund via `_refundERC20IfAny` — immediate, no grace period.** Safe because `cancelCampaign` is only reachable while `totalParticipants == 0`, which means no Merkle root could ever have been published (roots are set during Ended, which requires prior Open state where participants could have engaged) and no claim was ever possible. The `_erc20Swept` flag is set atomically with the transfer to prevent double-refund.
- **NFT reclaim — no auto-enumeration.** Escrowed NFTs are not auto-returned (no on-chain per-campaign inventory list). The host must call `withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155` with the specific tokenIds they know they deposited. `_requireSweepable` now returns early for `Cancelled` status (no grace wait needed, same rationale as ERC20 above).
- **`Cancelled` is a new terminal status.** No state transition out of `Cancelled` exists. Guards on Open/Ended/Closed-requiring functions all implicitly exclude it; `_requireSweepable`'s early-return is the only deliberate `Cancelled`-aware branch. Verify any future state guards also account for this fifth status.

## New surface added in the invariant-test pass (review focus)
- **Escrow-solvency invariant found finding #3 above** (cross-campaign ERC20 drain via `claimERC20` after sweep). This is the first bug this project's invariant/fuzz testing has caught — see `test/invariant/EscrowSolvency.invariant.t.sol`.
- **NFT inventory invariant confirmed no equivalent bug** for ERC721/ERC1155: `claimNFT` and `withdrawUnclaimedERC721/1155` check the *same* per-campaign escrow map, so a swept slice is already zeroed before a late claim could reach it. Fuzzed with a shared ERC1155 asset id across many campaigns specifically to stress the commingled-pool case (`test/invariant/NFTInventory.invariant.t.sol`).
- **Attestation-version invariant confirmed the signed-attestation replay guard holds** under adversarial fuzzing (stale-version replay, skip-ahead, non-signer, expired-deadline attempts) — the on-chain version only ever advances by exactly 1 via a genuinely valid next-version signature (`test/invariant/AttestationVersion.invariant.t.sol`).
- Foundry `[invariant]` config added (`foundry.toml`): 128 runs, depth 30, `fail_on_revert = false` (handler calls are expected to revert on bounded edge cases; ghosts stay consistent on discard).

## New surface added in Phase 2 (review focus)
- **`SIGNER_ROLE` key compromise** — a compromised signer can mint arbitrary task completions until revoked via `revokeRole(SIGNER_ROLE, ...)`. There is no on-chain rate limit or threshold; single-signer by design. Rotate quickly if compromised. See [TASK_VERIFICATION.md](TASK_VERIFICATION.md).
- **Zero-address participant guard** — `verifyTaskCompletionWithSignature` explicitly rejects `_participant == address(0)` (`Web3Campaigns__ZeroAddress`).
- **Signature replay/update model** — per-`(participant,campaign,task)` version counter; replay is impossible because the accepted version is advanced atomically. A signer *can* flip `completed` back to `false` by signing the next version — intentional (correction/re-verification path), but means partial completion counts may decrease for any off-chain aggregation that queries task state.
- **`completeTask` guard** — if any attestation has ever been accepted for a `(participant, campaign, task)` triple (`version > 0`), `completeTask` reverts `TaskManagedBySignature` to prevent mixing self-assertion and signer-controlled state.
- **Domain binding** — `verifyingContract` is encoded in the EIP-712 domain, so a signature produced for one deployment cannot validate against another. Tested in `test/SignatureVerification.t.sol`.

## New surface added in B1–B2 (review focus)
- ✅ **Escrow accounting now measures the amount actually received, not the nominal funding amount — FIXED.** `fundCampaignERC20` used to credit `_erc20Escrowed` with the caller-supplied `amount`, assuming a standard (non-fee-on-transfer) ERC20; a fee-on-transfer token would silently under-fund escrow. Fixed via `balanceOf(this)` before/after the pull — see the "fee-on-transfer ERC20 support" pass below.
- **Merkle root is host-controlled and updatable while Ended** — a malicious host can publish a root that omits/short-changes users (off-chain trust in the host's allocation). Escrow only guarantees funds *can't be rugged after commitment*, not that the allocation is fair. **Mitigated by `ROOT_DISPUTE_WINDOW` — see #14 and the pass note below.** Applies to both ERC20 and NFT roots.
- **NFT cross-campaign isolation** is enforced by the per-campaign `_escrowedERC721`/`_escrowedERC1155` ownership maps, now on `NFTSettlementModule` (tested: `test_ClaimNFT_CannotDrainNonEscrowedToken`). A campaign can only ever settle NFTs actually escrowed under it.
- NFT custody relies on OZ `ERC721Holder`/`ERC1155Holder`; `supportsInterface` resolves the `AccessControl` + `ERC1155Holder` diamond.
- ERC1155 over-allocation in a root is bounded by escrow: a leaf exceeding the escrowed balance reverts `NFTNotEscrowed` rather than over-paying.

## New surface added in the on-chain reward module + per-campaign pinning pass (review focus)
- **Single global `_onChainRewardModule` pointer was a mid-campaign rotation hazard (FIXED).** On-chain tiered settlement keeps all rank/score/tier state in a separately-deployed `OnChainRewardModule`, referenced by the admin-rotatable `_onChainRewardModule`. When that single pointer was the authorization basis for payouts, rotating it mid-campaign could **desync in-flight rank/score state** (a freshly-registered module has no record of completions the old one already tallied) or **lock an in-flight campaign out of payouts entirely** (the state-holding old module is no longer the registered one). Fix: each campaign **pins** its module once at adoption (`_campaignRewardModule[id]`, set in `setSettlementMode`, decoupled from the global default), and `payOnChainReward` authorizes against that pin alone (`RewardModuleMismatch`) — a rotation never moves authority for already-adopted campaigns. Tests: `test_PayOnChainReward_PinnedModuleStillPaysAfterRotation` / `_RevertsFromRotatedGlobalModule` / `_UnpinnedCampaignRejectsAllCallers` (`test/OnChainRewardModule.t.sol`).
- **`claimReward` self-check is defense-in-depth for a currently-UNREACHABLE path — do not remove it blind.** The module re-verifies `getCampaignRewardModule(id) == address(this)` before computing any payout (`OnChainRewardModule__NotAuthoritativeModule`). Today a campaign's pin **cannot be reassigned after adoption**, so no live path exists where an authoritative module holds stale state for a campaign that has moved elsewhere — this guard exists specifically so a **future** change adding re-pinning / module migration cannot silently reopen the desync/lockout class above without that author confronting it here. Test: `test_ClaimReward_NonAuthoritativeModuleReverts`.

## New surface added in the root dispute window pass (review focus)
- **`ROOT_DISPUTE_WINDOW` (24h) gates claims, not sweeps.** `claimERC20`/`claimNFT` reject claims against a root until `ROOT_DISPUTE_WINDOW` has elapsed since it was (re-)published (`Web3Campaigns__RootDisputeWindowActive`). Sweeps (`withdrawUnclaimedERC20`/`withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155`) were deliberately **not** given a separate explicit check: a sweep requires `Closed` + `CLAIM_GRACE_PERIOD` (30 days) after closing, and roots can only be set/updated while `Ended` (frozen at `Closed`) — so as long as `ROOT_DISPUTE_WINDOW` stays well below `CLAIM_GRACE_PERIOD` (documented at the constant), the dispute window on the final root has always long since elapsed by the time a sweep is reachable. If a future change ever shrinks `CLAIM_GRACE_PERIOD` close to or below `ROOT_DISPUTE_WINDOW`, this ordering assumption should be re-verified.
- **Rearmed only when the root VALUE actually changes — FIXED after review.** A host publishing a genuinely different root (e.g. fixing a bad allocation) restarts the window from scratch rather than inheriting the original publish's now-elapsed clock — an updated allocation deserves its own review period. The initial version rearmed on *every* call to `setERC20MerkleRoot`/`setNFTMerkleRoot` regardless of whether the root value changed; a manual PR review (not `no-mistakes`) caught that this let a host repeatedly "update" to the byte-identical root to indefinitely push out `claimableAt`, dangling participants at a *visibly published* root that never actually opens — a stronger complaint than the pre-existing "never publish at all" host-trust boundary, since it looks like progress without being any. Fixed: `setERC20MerkleRoot`/`setNFTMerkleRoot` now compare against the currently-stored root and only rearm on a genuine change. Tests: `test_ClaimERC20_SameRootRepublishDoesNotRearmWindow` / `test_ClaimNFT_SameRootRepublishDoesNotRearmWindow`.
- **Still not a full dispute-resolution system.** There is no on-chain flagging/veto actor for a specific root; the only escalation lever during the window is the existing blunt `EMERGENCY_ADMIN.emergencyPause()` (halts everything, not root-specific) or the host self-correcting. The window's value is purely giving off-chain verification time to happen before funds move.
- **Two new sentinel `== 0` checks** (`getERC20ClaimableAt`/`getNFTClaimableAt` returning 0 when no root was ever published) follow the same accepted low-risk-by-design pattern as #13 (`campaign.id == 0` etc.) — flagged by Slither's `incorrect-equality` detector, consistent with the rest of the codebase, not a new risk.

## New surface added in the protocol fee module pass (review focus)
- **`FeeModule` is a satellite contract, not inline logic — deliberately, for size reasons.** `Web3Campaigns` was at ~1.25KB headroom (24,576B EIP-170 limit) before this feature; a protocol fee added inline would have consumed most or all of it. Following the `OnChainRewardModule` precedent, fee computation lives in a separately-deployed `FeeModule` with its own budget; `Web3Campaigns` only integrates the narrow `IFeeModule.computeFee` call site, `setFeeModule`/`getFeeModule`, storage, two errors, and two events — costing ~503B of entrypoint headroom (now ~747B remaining, including the post-review `InvalidFeeTreasury` guard). Any future feature needing meaningful logic will very likely need the same satellite treatment.
- **No per-campaign pinning — a deliberate, reasoned omission, not an oversight.** The reward module needed pinning because it holds persistent per-campaign state (rank/score) that a rotation could desync from the pin used at payout time. `computeFee` has no equivalent: it is a pure function of `(amount, the module's current global config)`, fully evaluated and settled (fee transferred, escrow credited) within the single `fundCampaignERC20` call that invoked it. A rotation only affects funding calls made *after* it — the intended behavior, not a hazard. Test: `test_FeeModuleRotation_OnlyAffectsFutureFundingCalls`.
- **`computeFee` is a `view` call — reentrancy is structurally foreclosed, not just guarded.** Solidity compiles a call to an interface method declared `view` as a `STATICCALL`; the EVM itself reverts any `SSTORE` (or other state-changing opcode) attempted during that call, regardless of what the module's implementation tries to do. A malicious `_feeModule` cannot reenter `fundCampaignERC20` (or anything else) from inside `computeFee`.
- **Two defensive guards on `computeFee`'s return values, both unreachable through the reference `FeeModule` but reachable through any *other* module registered via `setFeeModule`** — an admin-trust boundary, same class as `_onChainRewardModule`: a misconfigured or malicious module can only harm campaigns funded after it is registered, and only up to what a host actually transfers.
  - `feeAmount > amount` → `Web3Campaigns__FeeExceedsAmount` (capped at `MAX_FEE_BPS = 1000`, i.e. 10%, enforced in both the reference module's constructor and `setFeeBps`). Converts a would-be arithmetic underflow Panic into a named, diagnosable error. Test: `test_FundCampaignERC20_RevertsIfFeeExceedsAmount` (deliberately-evil mock).
  - `feeAmount > 0 && treasury == address(0)` → `Web3Campaigns__InvalidFeeTreasury` (the reference module's constructor and `setTreasury` both reject `address(0)`). **Added after PR review** — the original version guarded `feeAmount` but not `treasury`, so a misbehaving module returning a nonzero fee with a zero treasury would have hit `safeTransfer(address(0), feeAmount)` directly: a self-inflicted funding DoS on standard OZ tokens (which revert on transfer-to-zero), or a silent burn of the skimmed fee on a permissive/non-standard token. Test: `test_FundCampaignERC20_RevertsIfTreasuryIsZeroAddress` (deliberately-evil mock); `test_FundCampaignERC20_ZeroFeeWithZeroTreasury_Succeeds` confirms the guard only fires when there's an actual fee to send.
- **`setFeeModule`'s missing zero-check on `_module`** (flagged by Slither) is the identical accepted pattern as `setOnChainRewardModule`: `address(0)` is a valid, intentional value that disables the feature entirely, not an oversight.
- **`FeeModule.admin` is a genuinely separate trust boundary from Web3Campaigns' `DEFAULT_ADMIN_ROLE` — deliberate, but deploy-time-relevant.** Documented in `FeeModule.sol`'s header: the module's `admin` is intentionally not required to be Web3Campaigns' own admin, so a project can run fee governance under separate keys/multisig if desired. The consequence worth being deliberate about: if the SAME key ends up holding both roles in practice, compromising that one key now also controls the fee rate and destination, not just campaign administration — a larger blast radius than existed before this feature. **Recommendation for production deployments: use a distinct key (ideally a multisig) for `FeeModule.admin`, separate from whoever holds `DEFAULT_ADMIN_ROLE` on `Web3Campaigns`.** No code change — this is a key-management decision made at deploy time, not something the contract can or should enforce (enforcing it would remove the deliberate flexibility to run fee governance separately).
- **`CampaignFundedERC20` now emits the NET escrowed amount, not the gross amount transferred from the host** (they're identical when no fee module is registered). No existing test asserted this event's payload before this change, so nothing broke — but any *new* off-chain indexer consuming this event should sum it together with `ProtocolFeeCollected` to reconstruct the host's gross payment.
- **Aderyn's High-1 bucket (reentrancy: state change after external call) gained a 7th instance, not a new category.** `computeFee` (a `view` call → `STATICCALL`) is flagged there alongside the four pre-existing `OnChainRewardModule` entries and two `ParticipantManagement` entries — a false positive, same class as those. Aderyn's category totals (High 1, Low 15) are unchanged, but "unchanged" should not be read as "no new finding anywhere" — precisely this one bucket did grow by one instance.

## New surface added in the NFT settlement module extraction pass (review focus)
- **`NFTSettlementModule` is a satellite contract, not inline logic — same size-reclaiming motivation as `FeeModule`, but larger blast radius since it's a custody-adjacent module, not a pure computation.** `Web3Campaigns` was at ~747B headroom before this pass; all NFT Merkle-settlement logic and per-campaign escrow bookkeeping was extracted into a separately-deployed `NFTSettlementModule` (its own EIP-170 budget, 4,664B used). `Web3Campaigns` reclaimed ~793B (now ~1,540B headroom) and kept **100% of NFT custody** — the module never holds tokens, only decides who gets paid what and calls back into the trusted `executeNFTTransferOut`. Unlike `FeeModule`, users call the module's entrypoints (`setNFTMerkleRoot`/`claimNFT`/`withdrawUnclaimedERC721`/`withdrawUnclaimedERC1155`) directly, not through a `Web3Campaigns` forwarding wrapper — mirroring `OnChainRewardModule.claimReward`'s shape, not `FeeModule.computeFee`'s.
- **Per-campaign pinning is required here (unlike `FeeModule`) — and pins at FIRST DEPOSIT, earlier than the reward module's pin-at-mode-adoption.** The module holds persistent per-campaign escrow state (which tokens/amounts are held for which campaign) that accumulates starting at the very first `depositERC721Rewards`/`depositERC1155Rewards` call — before any Merkle root could ever exist. Pinning at root-set time (mirroring the reward module) would leave a window between an unpinned deposit and a later root-set where a global-module rotation could orphan already-recorded escrow. `CampaignManagement._pinNFTModule` closes that window by pinning on the first deposit instead, idempotently, via `_campaignNFTModule[id]`. `Web3Campaigns.executeNFTTransferOut` authorizes solely against this per-campaign pin (`Web3Campaigns__NFTModuleMismatch` otherwise), identical in spirit to `_campaignRewardModule`/`RewardModuleMismatch`.
- **A direct, deliberate consequence: a campaign that never deposits an NFT can never call `setNFTMerkleRoot`.** It reverts `NFTSettlementModule__NotAuthoritativeModule` (the campaign was never pinned to any module). This is a strictly **stronger** security property than the pre-extraction behavior, not a regression — it blocks a cross-campaign-drain attempt one step earlier (at root-publish time, instead of only at claim time via the pre-existing per-campaign escrow-ownership check). Tests: `test_SetNFTMerkleRoot_RevertsOnNeverDepositedCampaign`, and `test_ClaimNFT_CannotDrainNonEscrowedToken` was updated to have the attacker's campaign deposit an unrelated token first (to get pinned) before publishing a fraudulent root, preserving the original drain-guard intent under the new pinning requirement.
- **Defense-in-depth self-check, same currently-unreachable-path caveat as the reward module.** Every `NFTSettlementModule` entrypoint re-verifies `getCampaignNFTModule(id) == address(this)` before acting on its own state (`NotAuthoritativeModule`). As with `OnChainRewardModule.claimReward`'s equivalent check, no live path exists today where an authoritative module holds stale state for a campaign pinned elsewhere (pins are set-once, never reassigned) — the guard exists so a **future** re-pinning/migration feature cannot silently reopen the desync bug class without its author confronting this check.
- **`IWeb3CampaignsForNFTModule.CLAIM_GRACE_PERIOD()`/`ROOT_DISPUTE_WINDOW()` are cross-contract getter calls, not direct constant references — a Solidity limitation, not a design choice.** `ContractName.publicConstantName` syntax only works for enums/library members without inheritance; a public constant on another (non-inherited) contract requires an actual external call through its auto-generated getter. Both are declared as `external view` on the interface and called via `IWeb3CampaignsForNFTModule(WEB3_CAMPAIGNS).X()`, same pattern already used for `getCampaignHostAndStatus`/`getCampaignClosedAt`/`getCampaignNFTModule`.
- **Aderyn's High-1 bucket (reentrancy: state change after external call) gained instances in `NFTSettlementModule`, not a new category.** The flagged lines are local escrow-state writes (`_nftLeafClaimed`, `_escrowedERC721`/`_escrowedERC1155`) following `view`/`STATICCALL` reads (`getCampaignHostAndStatus`, `getCampaignNFTModule`) earlier in the same function — the same false-positive class already accepted for `OnChainRewardModule`/`FeeModule`. Slither's naming-convention findings also grew (268 total, up from 249) purely from the new module's `_underscore`-prefixed parameters, the same already-accepted convention used everywhere else in this codebase.

## New surface added in the fee-on-transfer ERC20 support pass (review focus)
- **`fundCampaignERC20` now measures what actually landed via `balanceOf(this)` before/after the pull, instead of trusting the caller-supplied `amount` — FIXED, closing a documented-but-open gap.** Standard ERC20s make this a no-op (received == amount, byte-for-byte unchanged behavior and event payloads). A fee-on-transfer token skims its own cut in transit; crediting `_erc20Escrowed` with the nominal `amount` in that case would silently over-credit escrow beyond what the contract can ever actually pay out — a latent insolvency, not just a display bug, since `claimERC20`/`withdrawUnclaimedERC20` both pay from `_erc20Escrowed` accounting that would no longer be backed 1:1 by the contract's real token balance. New error `Web3Campaigns__NoFundsReceived` for the degenerate 100%-fee case (nothing arrives).
- **This necessarily reorders `fundCampaignERC20`'s CEI shape: the transfer-in interaction now happens BEFORE the escrow-accounting effect, not after — a deliberate, documented exception, not a lapse.** The received amount is only knowable once the pull completes, so the effect (`_erc20Escrowed[_campaignId] += escrowAmount`) cannot be computed any earlier. This is the same balance-diff pattern used throughout DeFi for the identical reason (Uniswap V2's `mint`/`burn`, and every other fee-on-transfer-aware vault). Safety comes from `nonReentrant` on the `Web3Campaigns.fundCampaignERC20` wrapper, not from strict instruction ordering — standard ERC20s (including fee-on-transfer ones) have no reentrancy hook to exploit here regardless, but the guard is what makes the exception unconditionally safe rather than merely "safe today."
- **Protocol fee (if a `FeeModule` is registered) is now computed on the RECEIVED amount, not the nominal one — consistent with the escrow fix, not a separate change.** `computeFee(id, received)` instead of `computeFee(id, amount)`; the contract can never be asked to skim a fee on funds it never actually custodied. A side effect worth knowing: the fee-payout leg (`safeTransfer(treasury, feeAmount)`) is itself just another transfer of the same token, so if that token is fee-on-transfer, the treasury nets less than `feeAmount` — the escrow accounting stays internally consistent regardless (the full `feeAmount` is debited from the contract's balance either way), it's only the treasury's *received* amount that can differ from the emitted `ProtocolFeeCollected(feeAmount)` value for such tokens. Not fixed further in this pass (would require repeating the same balance-diff defense on every outbound leg in the codebase); flagged here so a future change touching fee payout doesn't assume the emitted amount always equals what the treasury received.
- **Aderyn's High-1 bucket (reentrancy: state change after external call) gained 2 more instances on `fundCampaignERC20`'s existing entry (9 → 11 total), not a new category.** The `_erc20Escrowed` write is now flagged against three preceding calls instead of one (`balanceOf` ×2, `computeFee`) since the balance-diff pattern is itself two additional STATICCALLs before the same effect — same false-positive class, same `nonReentrant` mitigation, already accepted throughout this codebase. Aderyn's totals are otherwise unchanged (High 1 / Low 15, matching the pre-pass baseline). Slither gained exactly one new finding, `received == 0` (`incorrect-equality`) — the same accepted low-risk-by-design sentinel-check pattern as every other `== 0` finding in this codebase (#13).
- **New test file `test/FeeOnTransferERC20.t.sol`** with a minimal `FeeOnTransferMock` ERC20 (skims a configurable bps to a burn sink on every transfer) covers: escrow credited with the received amount not the nominal one, a 0%-fee token behaving identically to a standard token (regression guard), multiple funding calls accumulating correctly, the protocol-fee-on-received-amount interaction, and the `NoFundsReceived` degenerate case (153 tests total, up from 148).

## New surface added in the fee-on-transfer invariant coverage pass (review focus)
- **A 6th stateful-fuzz suite, `FeeOnTransferEscrowSolvency.invariant.t.sol`, fuzzes the same three escrow-solvency properties as `EscrowSolvency.invariant.t.sol` against a fee-on-transfer ERC20 instead of a standard token.** Follow-up flagged (non-blocking) during PR #12's review: the 5 fixed-point unit tests in `test/FeeOnTransferERC20.t.sol` cover the received-vs-nominal accounting fix correctly, but the invariant suite specifically built to catch escrow/balance drift across long random fund/claim/sweep sequences (`EscrowSolvencyHandler`) only ever wired up a standard `ERC20Mock`, so it couldn't exercise this exact scenario. This pass closes that gap with a dedicated handler/suite pair rather than parametrizing the existing one over two token types — mirrors this codebase's established pattern of one dedicated suite per concern (`RootDisputeWindow`, `NFTInventory`, `OnChainReward` are all separate files too), and avoids the added complexity of mixed-token per-campaign accounting in a single handler.
- **`FeeOnTransferEscrowSolvencyHandler` diverges from `EscrowSolvencyHandler` in exactly one structural way: ghost accounting tracks the amount ACTUALLY received per funding call, not the nominal amount requested** — measured via the same `balanceOf` before/after pattern the contract itself uses internally. The per-campaign allocation cap (`fundAmount / 4` in the original handler) is sized off the received amount instead, so claims stay non-vacuous (sum of allocations never exceeds what was actually escrowed) rather than bouncing off `InsufficientEscrow` for every fuzzed campaign.
- **Validated non-vacuous with a negative control before merge, following this project's established practice** (same discipline as `OnChainReward.invariant.t.sol`'s pinned-module negative control): temporarily reverted `fundCampaignERC20` itself (in `src/CampaignManagement.sol`, not the handler) to trust the nominal `_amount` instead of the measured `received` amount — reintroducing the exact bug PR #12 fixed, with the handler's own ghost tracking left correct — and confirmed `invariant_perCampaignBacked` failed immediately on the very first funding call in the fuzzed sequence, proving the suite genuinely catches a regression in the production fix rather than passing by construction. Reverted before merge. **Correction from PR #13's review**: an independent reproduction attempt broke the *handler's* `ghost_totalFunded` tracking instead of the contract (a different, also-valid experiment, but not the one actually run for this PR) and got a different failing invariant, `invariant_globalTokenAccounting` — expected, since that invariant is the one that reads `ghost_totalFunded` directly, while `invariant_perCampaignBacked` reads escrowed/distributed straight from the contract and never touches that ghost variable. Both invariants are real and both catch real regressions; they're just wired to different failure modes (contract-side bug vs. test-harness-side bug).
- **Distributed/escrowed ledger amounts are unaffected by the token's own skim on the claim/sweep outbound legs** — `_erc20Distributed`/`_erc20Escrowed` are debited by the full requested amount either way (the token's `_update` hook deducts the full amount from the sender's balance regardless of how much the recipient nets), so `invariant_distributedLeqEscrowed` and the balance-based invariants hold without needing separate accounting for what a participant/host actually received versus what left the contract's balance. Same nuance already documented for the protocol-fee-payout leg in the fee-on-transfer ERC20 support pass above.
