## Current state (2026-07-13)

`dev` has v0.3 escrow + Merkle settlement (PR #1), Phase 2 signature verification (PR #2), the invariant-test hardening pass including a real security fix (PR #3), `cancelCampaign` (PR #4), on-chain tiered settlement + per-campaign module pinning (PR #6), its invariant suite (PR #7), the Merkle root dispute window (PR #8), that window's own invariant suite (PR #9), the protocol fee module (PR #10), the NFT settlement module extraction (PR #11), fee-on-transfer ERC20 support (PR #12), its invariant coverage (PR #13), the hardening sweep — treasury-gated `withdrawETH`, `.code.length` token guards, multi-leaf NFT proof tests (PR #14) —, sponsored (gasless) claims + the Humanity gating spec (PR #15), deployment readiness — full-system deploy script + smoke test + runbook (PR #16) —, reward-configuration access-control invariant coverage (PR #17), the loud-revert re-verification (PR #18), and per-campaign `MAX_PARTICIPANTS_LIMIT` enforcement (PR #19) all merged. VERSION `0.5.0` on `dev`.

Active development on branch **`feature/permissionless-lifecycle`**: `endCampaign` is now **permissionless** — anyone (in practice the platform keeper) can end a campaign once its `endTime` has passed, so a campaign transitions on schedule even if the host abandons it. Closes a real fund-lockup (an abandoned Open campaign could never reach Ended, so participants could never claim). `openCampaign`/`closeCampaign` deliberately stay host-only. See [SECURITY_FINDINGS.md](SECURITY_FINDINGS.md).

**Recap (merged to `dev`):**
- **v0.3 (Stage A/B1/B2/B3)** — correctness fixes, then the reward system fully rebuilt as escrow + Merkle settlement for ERC20 and multi-standard NFT (ERC721 + ERC1155).
- **Phase 2** — off-chain task verification rebuilt as EIP-712 `SIGNER_ROLE`-signed attestations, replacing host-tx `verifyTaskCompletion`. Raised via the `no-mistakes` automated pipeline, which caught its own real bug (`TaskManagedBySignature`) during review.
- **Invariant hardening** — stateful-fuzz suites for escrow/settlement/attestation. **Found and fixed a real HIGH-severity bug that had been live on `dev`**: a cross-campaign ERC20 escrow drain via `claimERC20` (see [SECURITY_FINDINGS.md](SECURITY_FINDINGS.md) #3). Also raised via `no-mistakes`, which caught a methodological flaw in the fuzz-test design itself and a flaky coverage-guard.
- **On-chain tiered settlement + per-campaign module pinning** — RANK_TIERED/SCORE_TIERED via the separately-deployed `OnChainRewardModule`, with payout authority bound to a per-campaign pin rather than the rotatable global default (closes a mid-campaign rotation hazard). Its own stateful-fuzz invariant suite followed as a separate PR.
- **Merkle root dispute window** — `ROOT_DISPUTE_WINDOW` (24h) delays claims against a freshly-(re-)published root, giving the community time to catch an unfair allocation before funds move (see [SECURITY_FINDINGS.md](SECURITY_FINDINGS.md) #14). A manual PR review caught and fixed a self-griefing gap (same-root republish indefinitely stalling claims) before merge.
- **Root dispute window invariant coverage** — a 5th stateful-fuzz suite, covering both the ERC20 and NFT dispute-window paths via a ghost mirror of the rearm rule. Caught a real bug in the test handler itself (a missing `vm.prank`) during development.
- **Protocol fee module** — `FeeModule` satellite contract skims a flat `feeBps` at `fundCampaignERC20`, routed to a treasury; no per-campaign pinning needed since fee computation has no persistent per-campaign state to desync across a rotation.
- **NFT settlement module extraction** — all NFT Merkle-settlement logic + escrow bookkeeping moved into a new `NFTSettlementModule` satellite contract to reclaim entrypoint headroom; `Web3Campaigns` retains all NFT custody. Unlike the fee/reward modules, the NFT module needs per-campaign pinning (persistent escrow state) — pinned at **first deposit**, earlier than the reward module's pin-at-mode-adoption, since escrow bookkeeping can precede any root ever being published. PR review caught two real gaps before merge: a missing `is INFTSettlementModule` declaration (Aderyn's Missing Inheritance finding) and untested pause coverage (the module's claim/sweep functions lost their direct `whenNotPaused` wrapper) — both fixed, both now tested. See [SECURITY_FINDINGS.md](SECURITY_FINDINGS.md).
- **Fee-on-transfer ERC20 support** — `fundCampaignERC20` now credits escrow with the amount actually received (`balanceOf` before/after the pull), not the nominal `amount` requested, closing a previously-documented gap where a fee-on-transfer token would silently under-fund escrow relative to what the contract believed it held. Protocol fee (if registered) is likewise computed on the received amount. Standard tokens: byte-for-byte unchanged behavior.
- **Fee-on-transfer invariant coverage** — a dedicated `FeeOnTransferEscrowSolvency.invariant.t.sol` suite fuzzes the fee-on-transfer fix above against long random fund/claim/sweep sequences, mirroring `EscrowSolvency.invariant.t.sol` but against a `FeeOnTransferMock` token instead of a standard one. Validated non-vacuous with a negative control (temporarily reverted `fundCampaignERC20`'s fix in `src/CampaignManagement.sol`, confirmed `invariant_perCampaignBacked` fails immediately) before merge.
- **Hardening sweep** — three small backlog items: `withdrawETH` now sweeps to a stored admin-settable treasury (`setTreasury`) instead of an arbitrary caller-supplied address (clears Slither's `arbitrary-send-eth`, finding #10); a `_requireContract` (`.code.length`) guard rejects EOA/empty reward-token addresses in `configureERC20Reward`/`depositERC721Rewards`/`depositERC1155Rewards`; and the first multi-leaf NFT Merkle proof tests (all prior NFT claim tests used single-leaf/empty-proof roots).
- **Sponsored (gasless) claims** — permissionless `claimERC20For`/`claimNFTFor`/`claimRewardFor` entrypoints sharing their full bodies with the self-claim paths; rewards always go to the allocated account, never the caller, so a third party can only deliver an account's own allocation to its own wallet. Enables backend-paid gasless claiming with no meta-transaction framework. Shipped alongside [HUMANITY_GATING.md](HUMANITY_GATING.md) — the sybil-gating design (off-chain, no contract changes needed until Humanity Protocol ships an on-chain registry).
- **Deployment readiness** — the deploy script deployed only `Web3Campaigns`, predating the satellite split: NFT deposits, tiered rewards, and `withdrawETH` would all have reverted on a fresh deployment. Now deploys + wires everything, with a smoke test that calls the real script and runs all three reward paths end-to-end so it can't silently rot again. See [DEPLOYMENT.md](DEPLOYMENT.md).
- **Reward-configuration access-control invariant coverage** — closed the last open item on the hardening backlog. Unlike every prior suite (which fuzzes a single host — the handler itself), this one runs 3 distinct hosts, each with its own campaigns, repeatedly attempting `configureERC20Reward`/`depositERC721Rewards`/`depositERC1155Rewards` on each other's campaigns — must always revert `CallerIsNotHost`. Also surfaced a real methodological finding: this project's established "loud revert on unexpected success" handler pattern doesn't actually fail an invariant run under `fail_on_revert=false` (verified via negative control) — fixed in the new suite, flagged as a follow-up for the two pre-existing suites using it.
- **Loud-revert re-verification** — that follow-up. `AttestationVersionHandler.sol` and `RootDisputeWindowHandler.sol` both genuinely had the bug: disabling the checks each was built to catch (signer-role, deadline, and both contracts' dispute-window checks) produced **zero test failures** with the old pattern. `RootDisputeWindowHandler` was the more exposed of the two — its pre-existing invariants only ever checked claimable-*timing*, never that a claim actually respected it, so the broken loud-revert was the only thing watching at all. Both converted to the ghost-counter-only pattern and re-verified with the same negative controls.
- **Per-campaign participant limit** — `setMaxParticipants(id, cap)` lets each host set their own participant cap (Draft-only, `0` = unlimited and the default, hard-capped at the existing `MAX_PARTICIPANTS_LIMIT` constant as a sanity ceiling). Enforced in `completeTask`/`verifyTaskCompletionWithSignature` at the point a genuinely new participant would be counted; never blocks a wallet already counted from completing further tasks. `JOIN_COOLDOWN` removed rather than wired up — see [SECURITY_FINDINGS.md](SECURITY_FINDINGS.md) for the reasoning.
- **Permissionless `endCampaign` (in progress)** — `endCampaign` was host-only; now anyone can call it once `block.timestamp >= endTime`. Motivated by the "automated platform" goal (a keeper transitions campaigns on schedule) and a real fund-lockup fix (a host who opens a campaign then vanishes previously left it stuck in `Open` forever — no `Ended`, no claims, no escrow movement). The time gate binds every caller, so no one can end early. `openCampaign` stays host-only (opening is a "config is done" decision) and `closeCampaign` stays host-only (closing freezes the Merkle root; a permissionless close would enable a griefing freeze). Actually *reduced* contract size by dropping a modifier.

The contract is **escrow + verify + Merkle-settle**, plus an on-chain-computed dispute-free alternative for ERC20 tiered rewards. There is no live mid-campaign Merkle claim path. Off-chain rewards remain informational only.

Toolchain: Foundry 1.7.1, OZ + forge-std submodules initialized. **210 tests passing** (18 suites, including 7 stateful-fuzz invariant suites) on `feature/permissionless-lifecycle`. Build clean, `forge fmt --check` clean. Contract size 23,988B runtime (24,576B limit — **~588B headroom**; the permissionless-`endCampaign` change recovered ~57B by dropping a modifier, partly offsetting the participant-limit pass before it).

Decisions locked by the founder: **no upgradeability** (immutable, no proxy); **Merkle settlement after campaign end** is the reward claim model (not live mid-campaign); **`grantHostRole` stays open/unguarded** intentionally for now; **signature verification replaces** (not runs alongside) host-tx verification; **single `SIGNER_ROLE`** for now (no N-of-M threshold yet); replay guard = per-task version counter, which doubles as an update/reverification mechanism; **`cancelCampaign` requires zero participants** (no partial-cancel-after-engagement escape hatch).
